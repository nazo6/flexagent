# 複数下書きの保存と端末間同期

- **日付**: 2026-11-27
- **状態**: Partially Implemented
- **対象パッケージ**: `fxg-protocol`, `fxg-db`, `fxg-node`, `fxg-hub`, `ui`
- **対象スクリプト / 設定**: `crates/fxg-db/migrations/0006_drafts.sql`（新規）,
  `ui/src/lib/generated/bindings.ts`（生成物）,
  `ui/src/lib/stores/composer-drafts.ts`, `docs/02`, `docs/03`, `docs/07`

---

## 1. 背景と目的

現在のコンポーザーの下書きは、`ui/src/lib/stores/composer-drafts.ts` が
「セッション ID（新規セッション画面は固定 ID）→ テキスト 1 件」を
`localStorage` に保存するだけである。

- 1 つのコンポーザーにつき下書きは 1 件しか持てない
- 添付はメモリのみで、リロードや画面遷移で失われる
- 端末をまたげない。別の PC / PWA では同じ下書きを続きから書けない
- `localStorage` は容量が小さく、複数下書き + 添付の置き場には向かない

本提案の目的は、**未送信プロンプトを独立した複数の下書きとして保存し、
接続先ストア（ハブまたはノード）を経由して端末間で共有できるようにすること**。

### 1.1 決定事項（サマリ）

| 項目               | 決定                                                                                               |
| :----------------- | :------------------------------------------------------------------------------------------------- |
| 下書きの単位       | セッションに従属しない独立エンティティ。`session_id` は任意（`NULL` = セッションなし下書き）       |
| 保存先             | 接続先ストア。`node.db` / `hub.db` の単一スキーマ原則に従い両方に `drafts` テーブルを作る          |
| 同期               | REST + Client WS の変更通知。`session_events` / Outbox は使わない                                  |
| 競合解決           | `expected_revision` + `ErrorCode::RevisionMismatch`（設定 API と同じ楽観ロック）。自動上書きしない |
| 端末ローカルの状態 | 選択中の `draft_id`、オフライン用キャッシュ、未同期キューだけ。内容の正はサーバー                  |
| 添付               | v1 は本文のみ同期。添付は端末ローカル。共有は Phase 3 で content-addressed blob として行う         |
| node ⇔ hub 同期    | v1 では行わない。必要になったら Phase 4 で `revision` ベースの複製を追加する                       |

### 1.2 非目標

- 複数端末でのリアルタイム共同編集（CRDT / Yjs）。下書きは単一編集者を前提にする
- 下書きの暗号化。セッションイベントと同じ信頼境界（LAN / VPN + 認証）に置く
- 下書きの全文検索。必要になったら別提案とする
- 複数ユーザーでの共有。現状はセルフホストの単一ユーザーを前提とする

## 3. 設計方針

### 3.1 下書きはセッションの付属物ではない

下書きを `sessions` の子テーブルにすると、次のケースを表現できない。

- 送信先セッションをまだ決めていない下書き
- セッションをアーカイブ / 削除した後も残したい下書き
- 1 セッションに対して複数の候補プロンプトを持ち、選んで送りたい

そのため `drafts` を独立した集約とし、`session_id` は「あとで送る候補」として
任意に持つ。`session_id` に外部キーは張らない。ハブの `drafts` は他ノードの
セッションを参照し得るうえ、下書きはセッションより長生きするためである。
参照が切れた下書きは「Session deleted」としてセッションなし扱いで表示する。

### 3.2 書き込み権威は「接続先ストア」

下書きはエージェントではなくクライアントが書くデータである。したがって
セッションのような「実行ノードが唯一の書き込み権威」ではなく、
**UI が接続しているストア（ハブまたはノード）がそのスコープの権威**になる。

- ハブ接続時: `hub.db` が権威。ハブに接続する全端末で同じ下書きが見える
- ノード直結時: その `node.db` が権威。スタンドアロン構成ではこれで完結する

ハブは下書きをノードへ転送しない。下書きは実行状態ではないため、
`StartSession` / `SendPrompt` のようなコマンド経路には載せない。

### 3.3 イベントログ / Outbox は使わない

`session_events` は次の前提で設計されている。

- append-only で、実行ノードだけが `node_seq` を採番する
- セッションの実行履歴であり、FTS の検索対象になる
- ハブの `sessions` などはイベントから再構築する投影である

下書きは「クライアントが書く」「何度も書き換わる」「セッションに属さないものも
ある」ため、この前提に合わない。イベントとして積むと、キーストロークごとの
履歴でログが膨らみ、検索ノイズになり、削除の表現も不自然になる。

よって下書きは **専用テーブル + `revision`** で管理する。「同期はイベントログ
1 本」はセッション状態に対する原則であり、下書きはその対象外であることを
`docs/02` に明記する。

### 3.4 端末ローカルに残すもの

端末ごとに異なってよい状態は同期しない。未読状態や折りたたみと同じ扱いにする。

- いま編集中の `draft_id`（コンポーザーごと）
- オフライン中の本文キャッシュと未同期の変更
- 下書き一覧の並び順 / フィルタなどの表示設定

内容（本文・添付メタデータ・タイトル）だけをサーバーと同期する。

## 4. データモデル

`drafts` テーブルを `node.db` / `hub.db` の両方に作る（単一スキーマ原則）。
正となる DDL は `crates/fxg-db/migrations/0006_drafts.sql` に置き、ここでは
責務と不変条件だけを示す。

### 4.1 フィールド

| フィールド         | 型 / 既定                  | 責務                                                       |
| :----------------- | :------------------------- | :--------------------------------------------------------- |
| `draft_id`         | TEXT PK                    | UUID v7。作成端末に依存しない永続 ID                       |
| `title`            | TEXT NOT NULL DEFAULT ''   | 一覧表示用。空なら本文の先頭非空行から導出                 |
| `body`             | TEXT NOT NULL DEFAULT ''   | プロンプト本文                                             |
| `session_id`       | TEXT NULL                  | 送信先セッションの候補。外部キーなし                       |
| `project_id`       | TEXT NULL                  | セッションなし下書きを新規セッションへ渡すときの文脈       |
| `node_id`          | TEXT NULL                  | 同上（実行ノードの候補）                                   |
| `attachments_json` | TEXT NOT NULL DEFAULT '[]' | 添付メタデータ。v1 では端末ローカルの添付を参照するだけ    |
| `revision`         | INTEGER NOT NULL DEFAULT 1 | 更新のたびに +1。楽観ロックと変更通知に使う                |
| `origin_device_id` | TEXT NOT NULL              | 最後に書いた端末。デバッグと競合表示用（認証には使わない） |
| `created_at`       | INTEGER NOT NULL           | Unix epoch ms                                              |
| `updated_at`       | INTEGER NOT NULL           | Unix epoch ms。一覧の並び順                                |
| `deleted_at`       | INTEGER NULL               | 同期用の tombstone。NULL = 有効                            |

インデックス:

- `(updated_at DESC)` — 一覧
- `(session_id, updated_at DESC)` — セッションごとの下書き

### 4.2 不変条件

1. `draft_id` は作成端末をまたいで不変。複製時は新しい ID を採番する
2. 更新は `expected_revision` が現在の `revision` と一致した場合だけ成功する
3. 成功した更新は `revision` を +1 し、`updated_at` を更新する
4. 削除は物理削除ではなく `deleted_at` を設定し、`revision` を +1 する
5. `body` と `attachments_json` がどちらも空でも行は残してよい
   （タイトルだけの下書きを許可する）。空行の自動削除はしない
6. 一覧は既定で `deleted_at IS NULL` のものだけを `updated_at DESC` で返す
7. セッション削除時も下書きは削除しない。`session_id` はそのまま残し、
   読み出し時に存在しないセッションとして扱う

「空になったら消す」という現在の `#prune` の挙動は廃止する。複数下書きでは
「編集中の空スロット」と「保存済みの下書き」を区別する必要があり、
自動削除はユーザーの意図に反するため。

### 4.3 端末 ID

`origin_device_id` はブラウザプロファイルごとに一度だけ生成し、
`localStorage`（例: `fxg:device_id`）に保存する。サーバーは値の形式だけ検証し、
認証・認可には使わない。同じ端末からの変更通知を無視する（エコー抑制）用途と、
競合時に「どちらの端末が最後に書いたか」を表示する用途に限定する。

## 5. 同期モデル

### 5.1 v1: 接続先ストア内で完結

```
[端末 A] ──REST/WS──> [Hub (hub.db)] <──REST/WS── [端末 B]
[端末 C] ──REST/WS──> [Node (node.db)]        (スタンドアロン / 直結)
```

- ハブに接続している端末同士は、ハブを介して下書きを共有する
- ノードに直結している端末は、そのノード内で共有する
- 下書きの変更は既存の Client WS でブロードキャストし、他端末は一覧と
  開いているエディタを更新する

### 5.2 競合解決

設定 API と同じ `expected_revision` 方式にする。

1. 端末は最後に取得した `revision` を保持する
2. `PATCH` に `expected_revision` を付ける
3. 一致しなければサーバーは `ErrorCode::RevisionMismatch` と現在の下書きを返す
4. 端末は「最新を読み込む / 自分の内容で上書き / 両方残す（複製）」を提示する

自動の last-write-wins は行わない。プロンプトは書きかけの思考を含むため、
黙って片方を捨てるとユーザーは書いた内容を失う。競合時は必ずユーザーに
判断させる。

同じ下書きを 2 端末で同時に開いている場合、他端末の更新通知を受けたら
「別の端末で更新されました」と表示し、編集中の本文は勝手に置き換えない。
フォーカスが外れたタイミングで再読み込みを促す。

### 5.3 オフラインと再送

- デバウンス保存に失敗した変更は `localStorage` の未同期キューに残す
- 再接続時に `expected_revision` 付きで再送する
- 再送が `RevisionMismatch` になったら 5.2 の競合 UI に合流する
- オフライン中でも入力自体は失わない（現在の localStorage 保存と同じ保証）

### 5.4 node ⇔ hub（Phase 4、v1 では未実装）

v1 では「ハブ経由」と「ノード直結」を行き来すると下書きが見えない。
これを許容しない場合の拡張として、`revision` + `updated_at` +
`origin_device_id` による双方向複製を追加する。

- ノードは接続時にハブの下書き一覧を取得し、新しければ取り込む
- ノードで作った下書きは Outbox とは別の下書きキューでハブへ送る
- 削除は tombstone を複製し、一定期間後に GC する
- 同一 `draft_id` の同時更新は `updated_at` の新しい方を採用し、
  負けた側は複製として残す

セッションイベントの Outbox とは別経路になるため、実装する場合は
`docs/01` §2 に「下書きは複製対象だがイベントログには載せない」と明記する。

## 6. API / プロトコル

型は `crates/fxg-protocol/src/client_api.rs` に追加し、`specta` で
`ui/src/lib/generated/bindings.ts` へ出力する。ID は `ids.rs` の
newtype パターンに合わせて `DraftId` を追加する。

### 6.1 REST

| メソッド | パス                        | 内容                                                            |
| :------- | :-------------------------- | :-------------------------------------------------------------- |
| `GET`    | `/api/v1/drafts`            | 一覧。`session_id` / `project_id` で絞り込み、`updated_at DESC` |
| `POST`   | `/api/v1/drafts`            | 作成。`draft_id` はサーバー採番（UUID v7）                      |
| `GET`    | `/api/v1/drafts/{draft_id}` | 単体取得                                                        |
| `PATCH`  | `/api/v1/drafts/{draft_id}` | `expected_revision` 付き更新。不一致は `RevisionMismatch`       |
| `DELETE` | `/api/v1/drafts/{draft_id}` | 論理削除（tombstone）。冪等                                     |

- 認証・`Host` / `Origin` 検証は既存のミドルウェアに従う
- ノードとハブで同じ型・同じステータスコードを返す
- 一覧は下書きが小さいためカーソルページングは持たない。`limit` だけ任意で受ける
- `GET /api/v1/drafts?session_id=` はセッションなし下書きを返さない。
  セッションなしは `session_id` を省略した一覧で取得する

### 6.2 Client WS

`ServerWsMessage` に変更通知を追加する。

- `DraftChanged { draft_id, revision, deleted }`

本文は通知に含めず、端末が必要に応じて `GET` で再取得する。長文や画像を
WS に載せないための判断である。自分自身の `origin_device_id` による変更は
適用をスキップできる。

`ClientWsMessage` には下書き操作を追加しない。下書きは REST で完結させ、
WS は通知専用にする。コマンド相関（`command_id`）が不要なためである。

### 6.3 送信との関係

送信は既存の `SendPrompt` をそのまま使う。下書きは送信成功後にクライアントが
`DELETE` する。ノード / ハブに「送信と削除」を 1 トランザクションで処理させる
必要はない（失敗時に下書きが残る方が安全）。`SendPrompt` に `draft_id` を
追加しない。

## 7. UI

### 7.1 コンポーザー

- アクション行に「Drafts (n)」ボタンを追加し、ドロップダウンで
  下書きの切替・新規・複製・リネーム・削除を行う
- 既定の選択は「最後に更新した下書き」。無ければ新規作成
- 選択中の `draft_id` は端末ローカルに保存する
- 本文は 800ms のデバウンス + blur / `visibilitychange` で保存する
- 送信成功時は**その下書きだけ**削除する。失敗時は残す
- 1 セッションに複数下書きがある場合、一覧に本文の先頭行と更新時刻を出す

### 7.2 新規セッション画面

`NEW_SESSION_DRAFT_ID` 固定キーを廃止し、セッションなし下書き
（`session_id IS NULL`）の一覧から選ぶ形にする。

- 「New draft」で空の下書きを作成
- 既存のセッションなし下書きを選ぶと、その本文・添付・`project_id` /
  `node_id` を引き継いで新規セッションの入力に載せる
- セッション開始時はその下書きに `session_id` を設定し、最初の送信が成功した
  時点で削除する（送信に失敗した場合は残す）

### 7.3 サイドバー（任意）

セッションなし下書きを探すための「Drafts」ビューを追加する。プロジェクト別に
グループ化し、クリックで新規セッション画面に本文を引き継ぐ。v1 では必須とせず、
コンポーザーのドロップダウンだけでも成立させる。

### 7.4 セッション削除・アーカイブ時

下書きは残す。セッションが存在しない場合は「Session deleted」と表示し、
セッションなし下書きとして再利用できるようにする。

## 8. 添付

### 8.1 v1: 本文のみ同期

- `attachments_json` には添付メタデータ（ファイル名・MIME・サイズ・端末内の
  一時参照）だけを保存する
- 実体は端末のメモリ / ローカルに残り、他端末では復元できない
- 他端末で開いたときは「この端末の添付は引き継げません」と明示する
- 添付付きの下書きを別端末から送る場合は、本文だけ送るか、添付を選び直す

画像を `body` と一緒に DB へ入れると、数 MB の BLOB が WAL とバックアップを
圧迫するため、v1 では行わない。

### 8.2 Phase 3: content-addressed blob

添付も共有する場合の設計。

- `<data>/{hub,node}/drafts/blobs/<sha256>` に実体を置く
- `attachments_json` は `{ sha256, file_name, mime_type, size_bytes }` を持つ
- アップロードは下書き保存とは別の API（例:
  `POST /api/v1/drafts/blobs`）にし、返った `sha256` を下書きへ紐付ける
- 送信時にノードが blob を読み、既存の `AttachmentMeta.data_b64` または
  `local_path` へ解決する
- 参照カウントまたは定期 GC で、どの下書きからも参照されない blob を削除する
- サイズ上限と MIME 制限を設ける

## 9. セキュリティ・保持

- 下書きはセッションイベントと同じ信頼境界に置く。LAN / VPN 前提、
  既存の Bearer / Cookie 認証と `Host` / `Origin` 検証を必須にする
- プロンプトには秘密情報が含まれ得るため、監査ログの `details_json` に
  本文を出さない
- tombstone は同期のため一定期間残す（例: 30 日）。その後、物理削除する
  バックグラウンド処理を設ける
- ノードをハブから外した場合、`node.db` の下書きはノードに残る。
  v1 ではノードとハブの下書きは独立しているため、ハブ側の `hub.db` に
  残った下書きはそのままハブ接続端末だけで見える。削除するかは運用で決める
- 複数ユーザー対応をする場合は `owner_key` を追加する。v1 では持たない

## 10. 実装フェーズ

### Phase 1: 永続化と API

1. `crates/fxg-db/migrations/0006_drafts.sql` を追加
2. `fxg-db` に CRUD と楽観ロックを実装
3. `fxg-protocol` に `DraftId`, `Draft`, `DraftSummary`,
   `CreateDraftRequest`, `UpdateDraftRequest`, `DraftChanged` を追加
4. `fxg-hub` / `fxg-node` に REST を追加し、更新・削除を WS で通知
5. `mise run types` で bindings を更新

この時点では UI はまだ `localStorage` を使っていてよい。

### Phase 2: 複数下書き UI

1. `composer-drafts.ts` をサーバー保存 + ローカルキャッシュへ置き換える
2. `Composer.svelte` に下書きピッカー、複製、リネーム、削除を追加
3. `NewSessionChat.svelte` をセッションなし下書き一覧へ対応させる
4. 競合 UI と未同期キューの再送を実装

### Phase 3: 添付の共有

1. blob ストアとアップロード API
2. `AttachmentMeta` への解決
3. GC とサイズ制限

### Phase 4: node ⇔ hub 複製（必要になった場合）

1. 下書き用の複製キューと tombstone の伝播
2. 競合時の複製作成
3. `docs/01` への同期モデルの追記

| 案                                          | 却下理由                                                                    |
| :------------------------------------------ | :-------------------------------------------------------------------------- |
| `localStorage` に複数下書きを持つだけ       | 端末間共有ができない。容量と添付の制約も変わらない                          |
| `session_events` に下書きイベントを積む     | append-only / `node_seq` / FTS の前提に合わず、書き換えのたびに履歴が増える |
| `sessions` の子テーブルにする               | セッションなし下書きと、セッション削除後の保持を表現できない                |
| ハブがノードへ下書きを転送する              | 下書きは実行状態ではなく、ノードに置く必要がない                            |
| IndexedDB に保存して P2P / ファイル同期する | 端末ごとにストレージが分断され、既存のハブ認証・WS と統合できない           |
| CRDT でリアルタイム共同編集                 | 下書きは単一編集者で十分。複雑さに見合わない                                |

---

## 12. 未決事項

1. **共有範囲**: ハブ接続端末だけでよいか、ノード直結ともシームレスに
   したいか（Phase 4 の要否）
2. **添付**: v1 で本文のみとするか、最初から blob 共有を入れるか
3. **セッションなし下書きの導線**: サイドバーに専用ビューを置くか、
   コンポーザーのドロップダウンだけで足りるか
4. **保持期間**: tombstone の GC 期間と、削除済み下書きの復元を許すか
5. **下書きの上限**: 端末 / ストアあたりの件数・本文サイズの上限を設けるか

## 13. テスト

- `fxg-db`: 作成・更新・`revision` 不一致・論理削除・一覧順・
  `session_id` なしの絞り込み
- `fxg-protocol`: bindings の生成と JSON 往復（`DraftChanged` を含む）
- `fxg-hub` / `fxg-node`: 認証必須、`RevisionMismatch` のステータス、
  削除の冪等性、WS 通知が同一ストアの全クライアントへ届くこと
- `ui`: `composer-drafts` ストアの書き換え（複数下書き、選択の保持、
  競合時の複製、未同期キュー）。既存の `composer-drafts.test.ts` を置き換える
- 手動: 2 端末で同じ下書きを開き、片方の更新が他方へ通知されること。
  オフラインにして編集 → 復帰 → 競合 UI が出ること
